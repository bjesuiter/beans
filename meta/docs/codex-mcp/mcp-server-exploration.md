# Codex MCP server: how to consume it

_Last verified: 2026-03-17 against `codex` 0.114.0 on macOS._

This document describes the **actual behavior we observed locally** from:

```bash
codex mcp-server
```

It focuses on:

- how to start it
- how to talk to it over stdin/stdout
- the JSON input/output schemas it exposes
- how session management works in practice

---

## 1. Start the server

```bash
codex mcp-server
```

The process stays attached to stdin/stdout and does not print anything until you send JSON-RPC messages.

---

## 2. Important transport detail: it is JSONL over stdio

Although this command is named `mcp-server`, the current Codex CLI build we tested does **not** expect `Content-Length:` framed stdio messages.

It expects **one JSON-RPC message per line** on stdin, and emits **one JSON-RPC message per line** on stdout.

### What works

```text
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{...}}\n
```

### What did not work in our test

Standard MCP/LSP-style framing like this:

```text
Content-Length: 123\r\n\r\n{"jsonrpc":"2.0",...}
```

When we sent framed messages, Codex logged parse errors on stderr and did not respond.

### Practical implication

If you want to consume `codex mcp-server`, treat it as:

- **stdin**: JSONL
- **stdout**: JSONL
- **stderr**: logs/errors only

---

## 3. Minimal handshake

A minimal successful sequence is:

1. spawn `codex mcp-server`
2. send `initialize`
3. send `notifications/initialized`
4. send `tools/list`
5. call either `codex` or `codex-reply` via `tools/call`

### Example initialize request

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"my-client","version":"0.1.0"}}}
```

### Example initialize response

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2025-06-18",
    "capabilities": {
      "tools": {
        "listChanged": true
      }
    },
    "serverInfo": {
      "name": "codex-mcp-server",
      "title": "Codex",
      "version": "0.114.0",
      "user_agent": "codex_cli_rs/0.114.0 (...)"
    }
  }
}
```

### Supported protocol versions we verified

Both of these worked in our probe:

- `2024-11-05`
- `2025-06-18`

### Initialized notification

```json
{"jsonrpc":"2.0","method":"notifications/initialized"}
```

---

## 4. Server capabilities

From `initialize`, Codex currently advertises only tool capabilities:

```json
{
  "tools": {
    "listChanged": true
  }
}
```

In our probe it did **not** advertise resources or prompts.

---

## 5. Available tools

`tools/list` returned exactly two tools in our test:

- `codex`
- `codex-reply`

### `tools/list` request

```json
{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}
```

### `tools/list` response shape

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "tools": [
      {
        "name": "codex",
        "title": "Codex",
        "description": "Run a Codex session. Accepts configuration parameters matching the Codex Config struct.",
        "inputSchema": { ... },
        "outputSchema": { ... }
      },
      {
        "name": "codex-reply",
        "title": "Codex Reply",
        "description": "Continue a Codex conversation by providing the thread id and prompt.",
        "inputSchema": { ... },
        "outputSchema": { ... }
      }
    ]
  }
}
```

## 6. Input schemas

## 6.1 `codex`

Use `codex` to start a **new** Codex conversation.

### Input schema

```json
{
  "type": "object",
  "required": ["prompt"],
  "properties": {
    "approval-policy": {
      "type": "string",
      "enum": ["untrusted", "on-failure", "on-request", "never"],
      "description": "Approval policy for shell commands generated by the model."
    },
    "base-instructions": {
      "type": "string",
      "description": "The set of instructions to use instead of the default ones."
    },
    "compact-prompt": {
      "type": "string",
      "description": "Prompt used when compacting the conversation."
    },
    "config": {
      "type": "object",
      "additionalProperties": true,
      "description": "Overrides for CODEX_HOME/config.toml."
    },
    "cwd": {
      "type": "string",
      "description": "Working directory for the session."
    },
    "developer-instructions": {
      "type": "string",
      "description": "Developer instructions injected as a developer role message."
    },
    "model": {
      "type": "string",
      "description": "Optional model override."
    },
    "profile": {
      "type": "string",
      "description": "Config profile from config.toml."
    },
    "prompt": {
      "type": "string",
      "description": "Initial user prompt."
    },
    "sandbox": {
      "type": "string",
      "enum": ["read-only", "workspace-write", "danger-full-access"],
      "description": "Sandbox mode."
    }
  }
}
```

### Notes

- `prompt` is the only required field.
- `cwd`, `sandbox`, `model`, `profile`, `developer-instructions`, and config overrides are only available on the **initial** `codex` call.
- If you need a different sandbox/model/cwd later, start a new session with `codex` rather than trying to mutate an existing one.

---

## 6.2 `codex-reply`

Use `codex-reply` to continue an **existing** in-memory Codex conversation.

### Input schema

```json
{
  "type": "object",
  "required": ["prompt"],
  "properties": {
    "conversationId": {
      "type": "string",
      "description": "DEPRECATED: use threadId instead."
    },
    "prompt": {
      "type": "string",
      "description": "Next user prompt."
    },
    "threadId": {
      "type": "string",
      "description": "Thread id for the Codex session."
    }
  }
}
```

### Notes

- The schema only marks `prompt` as required, but in practice you must provide **either**:
  - `threadId`, or
  - deprecated `conversationId`
- If you omit both, Codex returns a tool-level error result:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "Failed to parse thread_id: either threadId or conversationId must be provided"
      }
    ],
    "isError": true
  }
}
```

---

## 7. Output schemas

Both tools advertise the same output schema.

```json
{
  "type": "object",
  "required": ["threadId", "content"],
  "properties": {
    "threadId": { "type": "string" },
    "content": { "type": "string" }
  }
}
```

### Actual `tools/call` result envelope

The schema above appears in the `structuredContent` field of the MCP tool result.

A successful call looks like this:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "PONG"
      }
    ],
    "structuredContent": {
      "threadId": "019cfc5e-3d0e-7702-921e-356e883d63cc",
      "content": "PONG"
    }
  }
}
```

### Important client-side rule

For machine consumption, prefer:

- `result.structuredContent.threadId`
- `result.structuredContent.content`

The `result.content` array is useful for generic MCP UIs, but `structuredContent` is the stable machine-friendly payload.

### Tool-level errors

Codex may return a normal JSON-RPC success response whose tool result is an error:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "Session not found for thread_id: ..."
      }
    ],
    "structuredContent": {
      "threadId": "...",
      "content": "Session not found for thread_id: ..."
    },
    "isError": true
  }
}
```

So clients should check **both**:

1. JSON-RPC transport success/failure
2. `result.isError === true`

## 8. Session management

## 8.1 Session handle = `threadId`

The session/conversation identifier returned by Codex is `threadId`.

You get it from the first `codex` call:

```json
{
  "structuredContent": {
    "threadId": "019cfc5e-8da9-76c2-976d-23601c6ff984",
    "content": "READY"
  }
}
```

Then continue the same session with `codex-reply`:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "codex-reply",
    "arguments": {
      "threadId": "019cfc5e-8da9-76c2-976d-23601c6ff984",
      "prompt": "What word did I ask you to remember?"
    }
  }
}
```

---

## 8.2 Sessions are in-memory for one server process

This is the most important session behavior we verified:

- a `threadId` works while the **same `codex mcp-server` process is still running**
- if you stop that server and start a fresh one, `codex-reply` with the old `threadId` fails with:

```text
Session not found for thread_id: <threadId>
```

So for MCP consumers:

- keep the `codex mcp-server` process alive as long as you want the conversation alive
- store `threadId` in your app state
- do **not** assume `threadId` is resumable across server restarts

### Practical implication

If you need durable conversations across app restarts, you currently need your own higher-level strategy, for example:

- keep a long-lived sidecar process running
- or replay prior conversation state into a new `codex` session
- or accept that Codex MCP sessions are ephemeral

---

## 8.3 What is inherited by `codex-reply`

`codex-reply` only accepts:

- `threadId` / `conversationId`
- `prompt`

That means the session continues with the settings established by the original `codex` call, such as:

- working directory
- sandbox policy
- approval policy
- model/profile
- injected instructions

If you need different execution settings, create a new session with `codex`.

---

## 8.4 Multiple sessions

You can manage multiple parallel Codex conversations by keeping multiple `threadId`s from the same server process.

Recommended mapping in a client:

- one long-lived `codex mcp-server` process
- many `threadId`s
- route each user/chat tab/work item to its corresponding `threadId`

---

## 9. Streaming and events

While a `tools/call` is running, Codex emits JSON-RPC notifications on stdout with method:

```text
codex/event
```

These notifications are useful for streaming UIs.

### Notification shape

```json
{
  "jsonrpc": "2.0",
  "method": "codex/event",
  "params": {
    "_meta": {
      "requestId": 2,
      "threadId": "019cfc5e-3d0e-7702-921e-356e883d63cc"
    },
    "id": "2",
    "msg": {
      "type": "agent_message_delta",
      "delta": "ONG"
    }
  }
}
```

### Fields to pay attention to

- `params._meta.requestId`: ties the event back to the originating `tools/call`
- `params._meta.threadId`: the Codex session/thread
- `params.msg.type`: event type

### Event types we observed

- `session_configured`
- `mcp_startup_update`
- `mcp_startup_complete`
- `task_started`
- `raw_response_item`
- `item_started`
- `item_completed`
- `user_message`
- `agent_message_content_delta`
- `agent_message_delta`
- `agent_message`
- `token_count`
- `task_complete`

### Simplest consumption strategy

If you only need final answers:

- ignore `codex/event`
- wait for the final `tools/call` response

If you need streaming UX:

- consume `codex/event`
- use `agent_message_delta` or `agent_message_content_delta` to update partial output
- treat final `tools/call` result as the authoritative completion payload

## 10. Minimal request/response examples

## 10.1 Start a session

Request:

```json
{"jsonrpc":"2.0","id":10,"method":"tools/call","params":{"name":"codex","arguments":{"prompt":"Reply with exactly: PONG","cwd":"/path/to/repo","sandbox":"read-only"}}}
```

Response:

```json
{
  "jsonrpc": "2.0",
  "id": 10,
  "result": {
    "content": [{ "type": "text", "text": "PONG" }],
    "structuredContent": {
      "threadId": "019cfc5e-3d0e-7702-921e-356e883d63cc",
      "content": "PONG"
    }
  }
}
```

## 10.2 Continue a session

Request:

```json
{"jsonrpc":"2.0","id":11,"method":"tools/call","params":{"name":"codex-reply","arguments":{"threadId":"019cfc5e-3d0e-7702-921e-356e883d63cc","prompt":"What did you just say? One word only."}}}
```

Response:

```json
{
  "jsonrpc": "2.0",
  "id": 11,
  "result": {
    "content": [{ "type": "text", "text": "PONG" }],
    "structuredContent": {
      "threadId": "019cfc5e-3d0e-7702-921e-356e883d63cc",
```

## 11. Minimal Node example

```js
import { spawn } from "node:child_process";
import readline from "node:readline";

const proc = spawn("codex", ["mcp-server"], {
  stdio: ["pipe", "pipe", "pipe"],
});

const rl = readline.createInterface({ input: proc.stdout });
const errRl = readline.createInterface({ input: proc.stderr });

function send(msg) {
  proc.stdin.write(JSON.stringify(msg) + "\n");
}

rl.on("line", (line) => {
  const msg = JSON.parse(line);
  console.log("STDOUT", msg);
});

errRl.on("line", (line) => {
  console.error("STDERR", line);
});

send({
  jsonrpc: "2.0",
  id: 1,
  method: "initialize",
  params: {
    protocolVersion: "2025-06-18",
    capabilities: {},
    clientInfo: { name: "example-client", version: "0.1.0" },
  },
});

send({
  jsonrpc: "2.0",
  method: "notifications/initialized",
});

send({
  jsonrpc: "2.0",
  id: 2,
  method: "tools/list",
  params: {},
});

send({
  jsonrpc: "2.0",
  id: 3,
  method: "tools/call",
  params: {
    name: "codex",
    arguments: {
      prompt: "Reply with exactly: PONG",
      cwd: process.cwd(),
      sandbox: "read-only",
    },
  },
});
```

## 12. Recommended client rules

If we build against this server, the safest assumptions are:

1. **Use JSONL, not Content-Length framing.**
2. **Always initialize first.**
3. **Treat `structuredContent` as the machine-readable result.**
4. **Check `result.isError`, not just JSON-RPC errors.**
5. **Persist `threadId` only for the lifetime of the same server process.**
6. **Keep one long-lived server process if you want multi-turn chats.**
7. **Use `codex/event` only for streaming/progress UI; final state comes from `tools/call`.**

---

## 13. Short summary

The current `codex mcp-server` is effectively a **JSONL JSON-RPC stdio server** exposing two tools:

- `codex` → start a new session
- `codex-reply` → continue an existing in-memory session

The key session handle is `threadId`, returned in `structuredContent.threadId`.
That `threadId` is **not durable across server restarts** in the current behavior we observed.
